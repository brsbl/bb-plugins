# Prove responsive behavior across the size range

Evidence for a user-visible change must cover each applicable size class the product supports, and the transitions between them, not one convenient width.

## Why

Layout fails at the edges and in between, so a single screenshot at the working size proves only that the size nobody complains about still works.

## Prefer

- Record one exact rendered size in each applicable class, from the smallest supported up to the largest.
- Resize through adjacent classes and inspect representative intermediate widths, not only separately loaded endpoints.
- Inspect populated and sparse content at each size, watching for overflow, clipping, wrapping, and unexpected gaps.

## Avoid

- One screenshot at the default size standing in for responsive behavior.
- Loading each width fresh and never observing the transition.
- Reporting approximate or labelled sizes instead of the exact rendered dimensions.

## Use when

- A change affects layout, styling, or anything whose rendering depends on available width.

## Do not use when

- The surface renders at exactly one fixed size that the user cannot change.

## Evidence

- Visual QA guidance requires an exact rendered size per class, inspection of transitions and intermediate widths, and sparse as well as populated content.

## Check

- Is there evidence at the narrowest and widest supported sizes?
- Was the transition between classes observed, or only the endpoints?
- Are the recorded dimensions exact rather than approximate?
