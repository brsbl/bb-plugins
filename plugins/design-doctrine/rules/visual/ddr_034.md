# Reflow from the container, not the viewport

A surface the user resizes independently of the window must key its breakpoints to its own width; viewport breakpoints misreport a narrow panel inside a wide window.

## Why

Window width says nothing about how much room a resizable panel actually has, so viewport-driven rules put multi-column grids and single-line control rows into a surface too narrow to hold them.

## Prefer

- Drive layout changes from the surface's measured width.
- Keep one measurement as the source of truth when CSS and code both branch on size.

## Avoid

- Viewport media queries inside a resizable panel, split pane, or embedded surface.
- Code that measures the window while its stylesheet measures the container.

## Use when

- The surface can be resized independently of the window, or is embedded in a host that sizes it.

## Do not use when

- The surface always spans the viewport, such as a full-page route or a window-sized overlay, where viewport width is the real constraint.

## Evidence

- Asked that a resizable plugin panel stay usable from a narrow side panel to full width, without clipping or overflow.

## Check

- Does every breakpoint on this surface read the surface's own width?
- Do the CSS breakpoints and any measured-in-code thresholds agree?
- At its narrowest supported width, does the layout still reflow instead of overflowing?
