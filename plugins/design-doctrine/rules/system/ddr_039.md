# Reduce concepts before adding them

Every new noun, screen, setting, or control adds to what the product costs to learn; extend or combine an existing primitive, infer instead of configuring, and automate instead of exposing a control.

## Why

Features are easy to add and expensive to carry, and the best version of a capability is often one the existing system already supports without a new concept.

## Prefer

- Extend an existing primitive, or generalize one, before introducing another.
- Infer from context and history instead of asking the user to configure.
- Automate a repeated decision rather than surfacing it as a choice.

## Avoid

- A dedicated screen, setting, or one-off control for something an existing surface already owns.
- Two concepts that mean the same thing to the user.
- An object that exists only to serve a single feature.

## Use when

- A proposal introduces a new object, screen, setting, permission, or control.

## Do not use when

- The capability genuinely cannot be expressed by existing primitives without producing a worse mental model, which should be stated explicitly.

## Evidence

- Capability guidance treats each addition as product debt and prefers extending, combining, generalizing, inferring, and automating.
- Critique guidance audits for features to remove, decisions to automate, and configuration that should become inference.

## Check

- Which existing primitive could carry this instead?
- What could be inferred rather than configured?
- Which new noun or control could disappear without losing the capability?
