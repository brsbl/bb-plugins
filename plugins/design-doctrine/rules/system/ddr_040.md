# Resolve the capability model before designing its UI

Describe a new capability independently of its interface first — inputs, outputs, state, lifecycle, ownership, permissions, relationships — and only then design the screens.

## Why

An interface drawn over an unresolved model encodes the gaps as layout, and the missing lifecycle stage or ownership question resurfaces later as a redesign.

## Prefer

- State what the object is, who owns it, and what it relates to before drawing it.
- Define the full lifecycle: creation, editing, viewing, finding, sharing, history, deletion, and recovery.
- Check the model at realistic scale before committing to a layout.

## Avoid

- Designing screens for an object whose ownership or lifecycle is still undecided.
- Treating a layout as the specification of the underlying capability.

## Use when

- The capability, primitive, or object being designed is new or not yet settled.

## Do not use when

- The capability model is already established and the task is a change to an existing surface within it.
- The gap is minor and the user asked for momentum, in which case state the assumption and continue.

## Evidence

- Capability guidance models inputs, outputs, state, lifecycle, permissions, ownership, and relationships before any interface.
- Design guidance defers to the capability model when the underlying primitive is unresolved.

## Check

- Can the object be described without reference to its screens?
- Is any lifecycle stage still undefined?
- Does the model still hold at ten times the expected volume?
