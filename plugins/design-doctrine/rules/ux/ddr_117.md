# Be judicious with error banners and keep them short

Only surface failures that affect what the user can do now, keep error messages to at most two lines, and recommend only recovery steps that would plausibly fix the problem.

## Why

Notifying users about self-healing or non-impacting failures and giving generic 'reinstall' advice erodes trust.

## Prefer

- Silent recovery when the running instance is unaffected
- Concise causes
- Banner actions as icon buttons with tooltips

## Avoid

- Banners for failed reloads while the current instance runs fine
- Notifying about background service restarts
- Retry where retry cannot help
- Generic 'remove and reinstall' advice

## Use when

- Designing error, failure, or recovery states

## Evidence

- User pruned non-impacting banners, unhelpful retries, and long error copy in one failure-state review.

## Check

- Each banner names an impact and an action that can resolve it
- Message fits in two lines
