# Make destructive actions reversible

A destructive or risky action, including one an agent takes on the user's behalf, should be undoable; where it genuinely cannot be, prevent the mistake before it happens rather than confirming it away.

## Why

Reversibility is what lets people move quickly without fear, and a confirmation dialog transfers the risk to the user instead of removing it.

## Prefer

- Offer undo on the object that changed, for as long as the user might notice.
- Design the recovery path as part of the action, not as an afterthought.
- Prevent the invalid or damaging case before the user can commit it.

## Avoid

- Treating a confirmation prompt as a substitute for recovery.
- Irreversible agent-initiated changes to the user's own content or state.
- Destroying work that could have been preserved and restored.

## Use when

- An action removes, overwrites, merges, sends, or otherwise changes state the user would not want to lose.

## Do not use when

- The action is genuinely unrecoverable by nature, such as an external send or an irreversible third-party effect, where prevention and a clear final confirmation are the correct treatment.

## Evidence

- Standing design guidance requires destructive actions to be reversible or to carry a clear recovery path.
- Critique guidance verifies undo for risky and destructive actions as a rubric item.
- Capability guidance requires every object's lifecycle to define recovery from mistakes.

## Check

- Can the user undo this, and from where?
- If it cannot be undone, what prevents the mistake rather than confirming it?
- Does an agent-initiated version of this action leave the user a way back?
