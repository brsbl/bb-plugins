# Design every state, not only the happy path

Enumerate the states a surface can actually reach — empty, loading, success, error, disabled, permission-denied, partial, conflicting — and say for each what the user sees, what they can do, and how they recover.

## Why

A design judged only on its populated success state ships with the states users actually get stuck in left undefined, so recovery gets invented late and inconsistently.

## Prefer

- List the reachable states before proposing the layout, and design each one.
- Say what is preserved and how the user recovers in every failure state.
- Explain why a disabled control is disabled and what would enable it.
- Show what succeeded and what is missing when a result is partial.

## Avoid

- Presenting only the populated success state as the design.
- Leaving loading, permission, conflict, or partial states to implementation.
- A state that tells the user something went wrong without a next step.

## Use when

- A surface can reach more than one state, or depends on data, permissions, or work that can fail.

## Do not use when

- The artifact is static and stateless, such as a printed or exported document with no interactive lifecycle.

## Evidence

- Standing design guidance requires each state to define what the user sees, can do, and how they recover.
- Critique guidance verifies empty, loading, success, error, disabled, permission, conflict, and undo states as a rubric.
- Visual QA guidance requires negative and transitional states to be inspected, not only the happy path.

## Check

- Which states can this surface actually reach?
- Does every failure state name what was preserved and the way forward?
- Is any state left to be decided during implementation?
