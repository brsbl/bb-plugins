# Make failure states honest and recoverable

A thing that fails or cannot resolve must say so in the user's terms and offer its recovery in the same place; never degrade silently, remove the object, or surface raw diagnostics.

## Why

Silent degradation hides the failure from the person who could fix it, and a failure named only in internal plumbing terms is a dead end even when the recovery is simple.

## Prefer

- Render an explicit unresolved or not-found state for an object that cannot resolve.
- Name the real condition in the user's terms and put the recovery action inline with it.
- Fuse the failure signal and its recovery into one control that visibly reads as clickable.
- Raise a blocking condition before the user spends effort on it.

## Avoid

- Degrading an unresolved object to ordinary content, or removing it outright.
- Raw runtime diagnostics, internal service names, and stack traces in a user-facing state.
- A failure notice that states the problem but not the next step.
- Heavy error chrome that shouts louder than the recovery it offers.

## Use when

- A reference, action, resource, or dependency fails, is blocked, or cannot resolve.

## Do not use when

- The surface has no content yet and nothing has failed, which is semantic absence rather than failure.

## Exceptions

- **The failure is not actionable by this user.** State the condition plainly and route to who or what can act, rather than inventing a recovery the user cannot perform.

## Evidence

- Required an unresolvable reference to show an explicit unresolved state instead of silently becoming plain content.
- Called a blocked state a dead end and asked for the real cause named plainly with the recovery step inline.
- Rejected raw runtime diagnostics in a problem state and required the condition and its fix in user terms.
- Asked a failure signal and its retry to be fused into one control that reads as clickable.
- Rejected invalid embeds rendering as ghost nodes and required an explicit not-found representation.
- Asked errors to be presented quietly inside the existing message system, each with its own next step.
- Rejected silently removing a reference whose target went missing, in favor of a recoverable warning.

## Check

- Does every failure state name the condition in the user's terms?
- Is the recovery available in the same place, and does the control look clickable?
- Does anything fail silently, degrade, or disappear without telling the user?
