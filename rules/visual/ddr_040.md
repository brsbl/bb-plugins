# Normalize repeated control geometry

Treat a header, toolbar, or other cluster of peer controls as one small system: one semantic gap token between visible edges, and shared control-box and glyph-size tokens so peer icons are equal.

## Why

Individually tuned peers drift apart, and the eye reads uneven gaps and unequal icons as meaning. Owning the geometry in shared tokens keeps the cluster uniform when items change state, labels vary, or controls move between equivalent groups.

## Prefer

- Use one semantic gap token between adjacent items, including matching left and right clusters.
- Measure spacing between visible boundaries; a selected or active background fill is the boundary, not the text or layout box.
- Use shared control-box and icon-glyph size tokens so peer icon buttons have equal targets and visibly equal icons.
- Put any optical compensation in the shared component or token, with the reason documented.

## Avoid

- Local margins and per-icon size overrides.
- Gaps measured from text while an active fill changes the visible edge.

## Use when

- A row or cluster of peer controls, such as a header or toolbar, shares one role.

## Do not use when

- Equal coordinates would harm optical balance, meaningful grouping, useful density, or the space left for content; alignment and uniformity serve readability and scanning, not themselves.
- The controls are not peers and deliberately differ in hierarchy.

## Evidence

- Asked peer header and toolbar controls to share one gap measured between visible edges, with selected fills as the edge, and equal icon box and glyph sizes from shared tokens instead of local overrides.

## Check

- Do adjacent items use one visible-edge gap, including when an item is selected?
- Do equivalent left and right clusters use the same gap token?
- Do peer icon buttons share control-box and glyph tokens, producing equal targets and visibly equal icons?
- Is any optical exception owned and documented at the shared component or token level?
