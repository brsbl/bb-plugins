# Prove visual work with current rendered evidence

Do not infer visible UI correctness from source text. Inspect the current rendered target, exercise the user journey through the real interface, and show the result with current product UI and realistic inputs; reject fake, stale, low-resolution, or cramped evidence.

## Why

Source can be correct while runtime composition, state, density, or stale assets remain visibly wrong, and an unrealistic or stale demonstration prevents an honest judgment of whether the work succeeds.

## Prefer

- Inspect the current rendered target in the relevant state and viewport.
- Exercise the outcome through the rendered user journey, not an API shortcut.
- Use current product UI with realistic, safe content, framed around the user job.
- Report what was observed separately from what source implies, and inspect final-resolution assets.

## Avoid

- Declaring UI correct because code looks correct.
- Stale, fake, placeholder, low-resolution, cropped, or cramped captures that hide the behavior.
- Using an unverified build or API-only proof for a user-visible capability.

## Use when

- An agent explains, reviews, or claims completion of visible UI work.
- A visual artifact is used to approve, document, or gate a design outcome.

## Do not use when

- The task is explicitly source-only and visual state is out of scope, which must be stated.
- A rough conceptual sketch is explicitly the requested stage and is labeled conceptual.

## Evidence

- Questioned an agent's claim about rendered content and requested a canvas screenshot capability.
- Reported a valid callout existed on disk but was absent from the rendered canvas because inspection never checked the visual result.
- Required rendered screenshots to be captured and posted inline as workflow gates are passed.
- Requested real, matching examples across feature visuals and removal of decorative or floating UI that distorted the demonstration.
- Requested current, high-resolution, uncrowded screenshots that show the relevant surrounding interface.
- Rejected prototype-only, broad visual changes and required minimal changes be applied to the real component stories.
- Required milestone acceptance to run through rendered UI journeys; API shortcuts do not prove the user capability.

## Check

- Was the current rendered target inspected directly, in the relevant state and viewport?
- Was the capability completed through its real rendered interaction?
- Does the artifact come from current product state with realistic, publishable inputs?
- Does the report distinguish observed behavior from inference?
