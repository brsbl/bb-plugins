# Show each status once, on the control that owns it

Encode installed, running, paused, and similar state once, as a distinct state of the owning control; do not repeat that status or other metadata already clear from the surrounding object, and do not add competing toggles.

## Why

Duplicated state labels and parallel controls create ambiguity about ownership and the next available action, and repeated metadata makes the differences that matter harder to scan.

## Prefer

- Let the owning control communicate current state and next action.
- Keep one canonical location for each status.
- Show only metadata that changes interpretation or the next action.

## Avoid

- Repeating the same state label throughout a row or between a row and its control.
- Adding a second toggle that competes with the primary state control.
- Text that restates status an icon or owning section already conveys.

## Use when

- A resource has a persistent state and a related action.
- A dense surface repeats descriptive or status text.

## Do not use when

- A separate status is needed for monitoring at a different scope.
- Redundancy is required for accessibility, safety, or cross-context orientation.

## Evidence

- Requested installed state be represented on its button rather than as a card-wide hover replacement.
- Rejected duplicated installed and paused state labels across related resource rows.
- Asked repeated run-state text be removed where an icon already communicates the status, carrying overview context into detail rows.
- Rejected duplicate status labeling and unnecessary inline detail navigation.

## Check

- Where is the canonical state shown, and is it shown only once?
- Does the owning control reveal the next valid action?
- Does each remaining metadata item change a decision?
