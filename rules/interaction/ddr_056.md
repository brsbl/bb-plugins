# Keep display-alias editing in its organizing context

Keep bb worktree display-alias editing in the sidebar, where it clearly renames an organizing row; avoid promoting it as a worktree rename in the composer or Info panel.

## Why

A prominent worktree rename action can imply changing the underlying resource when it only changes sidebar display metadata.

## Prefer

- Expose alias editing from the sidebar organizing row.
- Continue displaying user-assigned aliases where useful.

## Avoid

- Add name prompts or rename actions that imply changing the worktree itself.
- Making metadata editing more prominent without clarifying its actual effect.

## Use when

- Choosing entry points for editing a worktree display alias.

## Do not use when

- An operation actually renames the underlying resource rather than its display alias.

## Evidence

- The user rejected composer and Info naming affordances because display-name editing was confusing, while the sidebar modal clearly edits an organizing row.

## Check

- Does the entry point make it clear that only an organizing label changes?
- Could users mistake the action for renaming a directory, branch, or Git worktree?
