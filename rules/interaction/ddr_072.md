# Disabling a plugin preserves the remaining workspace

When a plugin is disabled in bb, close its affected tabs while preserving other open splits. If its removal leaves no usable content, take the user directly to New thread without an unavailable-panel interstitial or a detour through the plugin workspace.

## Why

Disabling one plugin should remove that plugin from the current activity without displacing unrelated work or leaving a dead page in navigation history.

## Prefer

- Close only tabs belonging to the disabled plugin and keep the other split open.
- Use New thread as the fallback when the disabled panel was the only usable content.
- Keep Back navigation from returning to the unavailable panel produced by disabling it.

## Avoid

- Redirecting the whole workspace to plugin management after disabling one plugin.
- Flashing an unavailable-panel page during an intentional disable.

## Use when

- Designing the transition after disabling a plugin with an open panel in bb.

## Do not use when

- Handling an unrelated plugin crash or an explicitly requested navigation to plugin management.

## Evidence

- During plugin QA, the user asked for a direct New thread fallback without an unavailable-page flash, and for disabling one split plugin to leave the other split open.

## Check

- With two plugins in splits, disable one and verify only its tab closes.
- Disable the sole open plugin panel and verify New thread appears without an unavailable-panel flash.
- Navigate Back after disabling and verify the removed panel does not reappear.
