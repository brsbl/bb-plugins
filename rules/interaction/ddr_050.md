# Derive extensible categories from real functionality

Build menu and discovery taxonomies from the actual items and their functionality, with an explicit placement rule for future items, including plugin contributions.

## Why

Invented labels and inherited categories can obscure what items do and leave future additions without a coherent home.

## Prefer

- Inventory existing items and their functions before naming groups.
- State how a new item is assigned to a group.
- Assess the taxonomy as a cohesive system that can accept new contributions.

## Avoid

- Inventing group names before reviewing the items.
- Preserving pre-existing categories without checking functionality.
- Adding new palette items without a clear place in the hierarchy.

## Use when

- Designing or revising categories for menus, plugin discovery, or command palettes.

## Do not use when

- Choosing the label for a single isolated action with no grouping system.

## Evidence

- For the composer menu, required a real inventory, derived groups, and a placement rule for new plugin items.
- For marketplace categorization, rejected invented categories and requested grouping all plugins by functionality.
- For the command palette, explicitly requested a cohesive system that makes new additions easy to place.

## Check

- Does each group describe the actual functions of its members?
- Can a new core or plugin item be categorized using the stated rule?
